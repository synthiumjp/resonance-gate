# Adversarial review, 2026-10-12 (product-p2 at 6d2c016)

Scope: claims against evidence, measurement integrity, product code,
launch readiness, and the own-material research direction. Read-only.
Nothing heavy was run on WSL; nothing was run on the Mac. Held-out case
text was never opened: where a check needed it, a subagent printed counts
only. "Verified" below means the code or file was read (or a count or
number recomputed) and the finding follows directly. "Suspected" means it
follows from reading but was not run.

Work was split across four Sonnet subagents (measurement integrity; block
assembly, pasted-text detection and parser; server security and privacy;
install and launch). The main findings of each were spot-checked against
the code before being listed here.

## The five things that matter most before launch, ranked

1. Claude Code sessions can store text the user did not write as the
   user's own words. The transcript reader skips only `isSidechain` and
   `isMeta` lines (server/sourcedrecall/claude_hooks.py:71), so the
   compaction summary Claude Code writes as a user-role message after
   /compact (marked `isCompactSummary`) would be stored and parsed as the
   user speaking. Separately, any agent can call `profile_ingest` with
   role "user", any date (including a future one, which then wins as the
   newest statement) and an existing conversation id; only standing
   instructions are filtered (mcp_server.py:277, profile_memory.py:285,
   371-381, 462). And ordinary paste intros turn someone else's text into
   the user's own: own cues are checked before source cues
   (prose.py:267 before 272), so "add this to my notes:", "help me quote
   this in my essay:", "my boss sent me this for my review:" (new in
   e9ef773) and a paste that contains "it's <owner's first name>'s" all
   return "own" (re-run on synthetic text, area 3.12-3.13). The product's
   one promise is "keeps your own words"; these paths break it. Fix
   before launch.

2. The pasted-text lead has not been separated from the instructions
   only sourcedrecall's reader gets, and the refusal rate behind it is not
   shown. On v10 sourcedrecall's block carries [MEMORY RULES] telling the
   reader that pasted text is never the user's (memory_api.py:159-175);
   plain retrieval and agentmemory get no such sentence. `FM_OURS_RULES=0`
   was run only on v3, v4, coding and projects (fair_run.sh:35), never on
   v6-v10, the pasted-text sets. Refusal-style answers on v10 (counts from
   a subagent): sourcedrecall 47 of 120, plain retrieval 18, agentmemory
   34, ai-memory 84; on own material all 7 of sourcedrecall's misses were
   refusals. Before the launch post leads with "3 of 40 against 23", rerun
   v9 and v10 answers from the saved retrievals with (a) our block without
   its rules and (b) plain retrieval with one added sentence about pasted
   text. If (b) gets close, the claim must change. Cheap: no retrieval
   rerun needed.

3. The public docs disagree with the evidence in several places and one
   key table is from a commit 45 commits old. README.md:31-33 still says
   the numbers "are being fixed before these numbers are used for any
   claim"; the false-memory table (README.md:58-65) is the fair rerun on
   372c05a, while the release script that produced the other numbers runs
   the same sets under the old, rejected protocol (tools/release_measure.sh
   has no FM_READER_SAME / FM_SAME_V7 / FM_STRICT / FM_JUDGE_QUESTION);
   HOW_IT_READS still calls pasted-text detection "supported" and says
   "messages are now quoted as written" (the code flattens every line
   break); CHANGELOG's Unreleased numbers are from 1754180 and it lists
   none of the 2026-10-09 security and privacy fixes. Details in area 1.

4. Install and trust basics. The installer clones a private repo; three
   of the six model downloads (bge-small, the MiniLM cross-encoder, the
   NLI model) come from the mutable `main` branch of third-party repos
   with no revision and no sha256 (experiments/p2/ort_models.py:53-59);
   no CI runs the 1,318 tests on any OS; the Windows lock silently runs
   unlocked after ~10 s (profile_memory.py:95-100); the secret filter
   backtracks quadratically on long hyphenated or dotted text (8 KB:
   2.7 s; 100 KB: minutes, on every stored turn; secrets.py:70-75); an
   unreadable conversations.json is treated as empty and overwritten on the next
   ingest or forget, losing the whole history (profile_memory.py:368-371
   and the `_erase` function at 1599+); the forget fingerprint is an
   unsalted sha256 of a short normalised sentence (profile_memory.py:1562)
   and conversation titles keep forgotten text, so README.md:271-274
   overstates what forget does.

5. The own-material work is deciding on noise with one reader. Changes
   are adopted or rejected on differences of 1-4 items out of 20-94 (own
   24 -> 26, 26 -> 25, "+3-4 false memories"), with one model at
   temperature 0 and no paired test. The rules wording is being tuned to
   Qwen3-14B's refusals, while a real user's reader is their agent's
   model. Before more wording or layout variants: a 2x2 on fixed
   retrieval (our lines vs plain retrieval's lines, with vs without our
   rules) to locate the cause, a second local reader to see whether the
   refusals are Qwen-specific, and a decision rule with McNemar on paired
   items fixed before each experiment. Details in area 5.

## Area 3. Product code

### Capture and storage (server/sourcedrecall)

3.1 Blocker (suspected; verify on a throwaway session). Compaction
summaries stored as user speech: claude_hooks.py:71 skips only
isSidechain / isMeta; no reference to isCompactSummary anywhere in the
server. A long model-written summary would be stored and parsed as the
user's words in every compacted session. Fix: skip lines with
isCompactSummary (and isVisibleInTranscriptOnly), and add a test with a
synthetic transcript.

3.2 Should fix. MCP write tools let an agent speak for the user (M1-M3
of the security subagent, read and confirmed): profile_ingest accepts
role "user", any ISO date including the future (profile_memory.py:285),
and an existing conversation_id to append to and rename (371-381);
profile_forget, profile_correct and profile_confirm are one call each,
forget is permanent, and confirm marks a fact owner-confirmed. No MCP
tool annotations (destructiveHint / readOnlyHint). profile_rehydrate
ignores project scope (profile_memory.py:1347) and does not bound
max_turns. Fix: store MCP-submitted turns as agent-submitted (or reject
role "user" from MCP), reject future dates and existing ids, add
annotations so the host asks the user, scope rehydrate.

3.3 Should fix. Data loss on an unreadable store. Ingest
(profile_memory.py:368-371) and `_erase` (1599+) catch a failed
json.load of conversations.json, carry on with an empty list, and write
it back: the whole history is replaced by one conversation (ingest) or
nothing (forget). Low probability, total loss. Verified. Fix: on a parse
failure, stop, keep the file, write a .corrupt copy and report.

3.4 Should fix. Forget is weaker than README.md:271-274 says. The
conversation title (first 60 chars of the first message) is not touched
by `_erase` (verified: it edits chat_messages text, the cache and
corrections only); only whole normalised sentences are removed, so an
assistant reply quoting the user, or the sentence inside a longer one,
stays; the Cursor spool keeps it up to 30 days; `forgotten.jsonl` holds
an unsalted sha256 of the lower-cased sentence (profile_memory.py:1562),
which a dictionary attack recovers for short sentences ("i have
diabetes"); `_erase` reports success without counting removals. Fix:
HMAC with a per-install key, erase titles and spool, substring removal,
return the count, and soften the README sentence.

3.5 Should fix. Windows locking fails open: msvcrt.locking(LK_LOCK)
retries for about 10 s then raises; the bare except (lines 95-100)
continues without a lock, and the lock is held across parsing, which can
exceed 10 s. That is the 10-09 lost-sessions bug back on Windows.
Verified by reading; behaviour on Windows not run. Fix: loop with a long
timeout and fail loudly; do not hold the lock while parsing.

3.6 Should fix. The hook builds the title from the first 60 characters
before the secret filter runs (claude_hooks.py:167-168, scrub later), so
a secret cut at character 60 is too short to match and part of it is
stored. Scrub, then truncate.

3.7 Should fix. Secret filter gaps (ran secrets.scrub on strings, no
models): PGP private key blocks, `Authorization: Basic ...`, `whsec_`,
bare `user:pass@host`, a 32-letter token with no digit, non-English
"password" words pass. Add patterns and tests.

3.8 Should fix. Cursor `stop` fires every agent turn and spawns a worker
that reloads the parser (cursor_hooks.py:130-135); workers queue behind
the lock at hundreds of MB each. Store on session end or debounce.

3.9 Should fix. Each ingest rewrites the whole conversations.json under
the lock (profile_memory.py:369-404): importing a large ChatGPT export is
quadratic. The importer's zip cap is 4 GB with whole-file reads
(importers.py:358): a big export can OOM the machine (the same failure
that killed this WSL box). Cap near 1 GB and stream.

3.10 Minor. Windows: start_new_session does nothing (claude_hooks.py:203,
cursor_hooks.py:156; use DETACHED_PROCESS); stdin decoded with the
locale codepage; open() without encoding= in several places (latent, the
files are ASCII JSON). chmod-based privacy is a no-op on Windows; say so.
`_OWN_SUMMARY` (claude_hooks.py:47) deletes everything after a typed
"[MEMORY" to the end of the message.

3.11 Minor. MCP tool docstrings (mcp_server.py:100-335) are long and use
research vocabulary ("p2 world/profile memory", "page table",
"rehydrate", "backing store"); profile_ingest's is ~40 lines. Twelve
tools with overlapping verbs cost context in every session and invite
the agent to call the write tools. Cut to 2-3 plain sentences; hide
export, quarantine, dynamics, rehydrate by default.

### Block assembly, pasted text, parser (experiments/p2, rgx)

3.12 Should fix (verified, ran prose._paste_span, pure regex, no models).
Own cues beat source cues, and possessive destinations read as
authorship. `_structure_span` returns "own" if `_FRAME_OWN` matches the
frame before it looks at `_FRAME_SOURCE` (experiments/p2/prose.py:267 then
272). With a council letter or a news article containing "I'm a
vegetarian and I have three kids", owner "Amara Okafor", each of these
intros makes the whole paste the user's own words:
"add this to my notes:", "save this in my journal pls:", "help me quote
this in my essay:", "found this, keep it for my notes", "summarise this
article for my notes:", and even "my neighbour forwarded this, can you
check my spelling in my reply after:" (an explicit source). All but one
were already "own" before e9ef773; e9ef773's `\bmy (?:own
)?(?:song|...|review|notes?|diary|journal|draft)\b` (prose.py:208-209)
added "my boss sent me this for my review:" (pasted before, own now).
"Here's the council's letter:" is still detected. These are ordinary
ways to paste someone else's text, and they turn straight into false
memories. Fix: a source cue ("sent me", "forwarded", "from my X",
"found") wins over an own cue; "my notes/journal/essay" counts as own only
as the subject or object of writing ("my notes:", "my essay draft"), not
after "to/in/for" ("add this to my notes"); add these as dev cases and
tests, and measure on pasted, pasted2 and own before and after.

3.13 Should fix (verified). The owner-signature and self-introduction
checks are loose (prose.py:299-309). The "initial" is `[A-Z]\.?` under
re.I, so any letter passes ("Regards, Thabo Z" or "Thabo K" on a boss's
email, owner Thabo Eze, returns "own"); a sign-off with the first name
alone also passes, so a relative or namesake is taken as the user; and
`\b(?:i'?m|i am|my name is|this is|it'?s)\s+<first>\b` is searched over
the whole paste, so "Hi all, it's Thabo's turn to cook. I live in Cork and
I am vegan." signed Anna, under "Summarise this email from my boss:",
returns "own" (I re-ran this one). Fix: require the owner's actual
initial, case-sensitive, on the last line only; restrict the
self-introduction to "I'm / my name is" in the first or last line; never
let first name alone override a source cue.

3.14 Minor. The advice pattern still fires on coding questions such as
"Where should I put the config file?" (`(?:what|which|where|how)...should
i`, memory_api.py:138); HOW_IT_READS.md:248-250 said it would be narrowed
and measured on a coding set. In advice mode the UNKNOWN sentence is
swapped and ranking changes.

3.15 Should fix before the line-break experiment ships. `_inert`
(memory_api.py:766-777) neutralises only "[MEMORY", "[pasted in" and the
notes marker, and relies on collapsing all whitespace to one line. If line
breaks are kept, a stored message can carry a line shaped like a block
line ("- [2026-09-01] \"...\"") or a "(no longer true: ...)" note. See
area 5.

3.16 Should fix, high (verified, timed). The secret filter backtracks
quadratically. The .env-style pattern in server/sourcedrecall/secrets.py:
70-75 (`\b(?![\w.-]*(?:error...` then `[\w.-]*(?:password|...)`) rescans
a long run of `[\w.-]` from every word boundary: "a-" repeated, then
"token=", takes 0.04 s at 1 KB, 0.68 s at 4 KB, 2.74 s at 8 KB (I re-ran
these); by the quadratic trend about 7 minutes at 100 KB. scrub() runs on
every stored turn (profile_memory.py:337, cursor_hooks.py:77) with no
length cap (before the store lock is taken, so it stalls the worker
rather than other writers). Pasted logs, lockfiles, minified code
and dotted identifiers are common in coding sessions. Fix: bound the run
(`[\w.-]{0,60}`), find the keyword first and look back, and chunk long
input; add a timing test.

3.17 Should fix (verified by the subagent). Credentials that survive the
filter: a value on the next line after "my password is" or "The
password"; "my pass is hunter2"; "Authorization: Basic ..."; short custom
auth headers; "Passwort:", "mot de passe:", "contraseña"; "key=AbC123dEf456";
PGP private key blocks; whsec_. Common formats (AKIA, ghp_, github_pat_,
xox*, sk_live, JWT, AIza, sk-proj, sk-ant, PEM keys, user:pass@ URLs,
Bearer) are caught. README.md:275-277 lists formats; keep it to what is
tested and say it is English-only.

3.18 Should fix (verified). A field list in the user's own message is
dropped as a chat log. `_CHAT_LINE`'s last alternative (prose.py:~164)
takes two "Capitalised: word" lines as speakers: "Allergies:
peanuts\nDiet: vegan\nCity: Leeds" gives prose_only == "" (re-ran), and
"Job: nurse\nHome: Leeds\nI have two kids" loses its first two lines. The
message is still stored and searchable, but the parser never reads the
facts. This is exactly the kind of own material (a profile, a checklist)
the open weakness is about. Fix: a speaker needs to recur, a time stamp
or three turns; field nouns are not speakers.

3.19 Should fix (verified by reading cases_dev_own.jsonl). e9ef773's new
own cues are fitted to the dev set: dev case do22 opens "wrote the chorus
last night, my song lyric for the band", which is the commit's quoted
example, and the noun list (song, lyric, chorus, verse, toast, eulogy,
bio, cv, listing, review, diary, journal) mirrors the set's subtypes. The
24 -> 26 gain is on the items the rules were written from. Treat it as
unmeasured until a held-out set; prefer generic frames ("I wrote", "my

## Area 5. Research direction: own material

What the data say (counts): on v10 own material sourcedrecall 13/20,
plain retrieval 19/20; all 7 of our misses are refusals; in 6 of 7 the
fact was in the block, 5 of them as plain user lines. On the pasted-claim
probes our reader refuses 35/40 against plain retrieval's 14/40. So the
same reader, given our block, refuses much more often across the whole
pasted-shaped region: right on the claims, wrong on the user's own
drafts. That is one behaviour with two signs, not an own-material bug.

Is the diagnosis sound? Partly. "The reader refuses with the fact in
the block" is established. "Why" is not, and the experiments so far
change several things at once or change too little to see:
- the own-writing note (24 -> 24) and rules-first (26 -> 25) are
  null results on n=40, not evidence against ownership or position;
- "shorter rules: +3-4 own, +3-4 false memories" changed several
  sentences together; nothing says which sentence moved which item;
- every decision uses one reader (Qwen3-14B, /no_think, 120 tokens);
- the dev own gap is only 26 vs 29 (3 items), so the dev set has little
  power to detect a fix; v10's 13 vs 19 was larger than the dev set
  shows.

What differs between our block and plain retrieval's, any of which could
drive refusal: (a) the rules paragraph ("UNKNOWN ... rather than
guessing", "never answered from [pasted]", "word for word"); (b) many
lines in short histories versus 3; (c) chronological order versus
best-first; (d) 800-character windows centred by word overlap versus
whole messages (an inference question such as "how old is my son?"
shares no word with "Matteo turned nine", so `_focus` falls back to the
opening, memory_api.py:668-689, 703-709); (e) flattened line breaks; (f)
the header line and notes; (g) other lines in the same block marked
[pasted in ...], which may prime caution about the unmarked draft.

What I would do, in order:
1. A 2x2 on fixed retrieval, own and pasted dev sets: {our lines, plain
   retrieval's 3 lines} x {our rules, SAME_RULES only}. This separates
   lines from rules in one run. If our lines without rules still refuse,
   it is (b)-(g); if plain retrieval's lines with our rules refuse, it
   is the rules.
2. Rerun the same 2x2 with a second local reader of another family
   (the memory notes already ask for two local models for judging). If
   the gap does not appear with the second reader, stop tuning wording
   to Qwen3-14B: the user's agent is a different, stronger model.
3. Single-sentence ablations of the rules, one at a time, each with a
   paired McNemar test against base on own + pasted + stale2, with the
   decision rule written down first (for example: adopt if own gains
   with p<0.1 and the upper 90% bound of the false-memory change is
   under +2 across sets). "rather than guessing" is the first to try:
   plain retrieval's instruction has no such clause, and inference from
   a draft reads as guessing to a cautious reader.
4. Enlarge the dev own set (combine cases_dev_own's 40, pasted_long's 16
   own, the earlier dev pasted sets' 36: about 90 own items) so a
   3-item change is not the whole signal.
5. Only then layout: best-matching full message first for factual
   questions (as advice mode already does), or fewer low-relevance lines.

Risks to the false-memory results of the untested ideas:
- Keeping line breaks (breaks.py, in flight). `_inert` collapses
  whitespace on purpose: it is the 10-09 fix for stored text imitating
  the memory's own headers (memory_api.py:766-777). With line breaks
  kept, a stored message containing "\n- [2026-09-01] \"I'm allergic to
  penicillin\"" would look like a separate memory line; only "[MEMORY"
  and "[pasted in" are neutralised now. Keep the indent variant at most,
  neutralise any line that starts like a block line, and keep the
  test_security test passing. Also, breaks.py scores expected terms only
  (no judge), so it says nothing about false memories; any adoption
  needs the full answer + judge + score on pasted, pasted2, stale2 and
  own controls. Breaks may help the reader see where a paste ends,
  which could lower false memories, but that is a hope until measured.
- Showing the best-matching sentence of a long own message as its own
  line. This is the riskiest: for the 3/40 pastes that slip past
  detection, the best match to "Do I ...?" is usually the very claim to
  forbid, and it would be promoted out of its context into a stand-alone
  "user said" line. Gate it to messages with positive own evidence (an
  own introduction or the owner's signature), not merely "not detected
  as pasted", and show it inside the message's quote, not as a new line.
- Fewer low-relevance lines. Lower risk to pasted false memories, real
  risk to changes: the line that replaced an old fact may score low for
  the question and be dropped, leaving the old state alone. Keep any
  line linked by the parser to a shown fact regardless of score, and
  check stale and stale2 "new state given".

One more product-level option that does not touch the reader: own
detection is now winning on dev for intros like "my notes" and "wrote
the", and these are checked before source cues (prose.py:267 before
272). That ordering means an own phrase anywhere in the frame makes a
paste the user's ("summarise this article for my notes:"). See area 3.
The cost runs both ways: the same module drops the user's own field
lists ("Diet: vegan / City: Leeds") as chat logs (area 3.18), a direct
own-material loss that wording changes cannot fix. Fixing detection in
both directions (source cue beats own cue; field lists are not chat) is
a cleaner own-material gain than any rules wording, and its false-memory
risk can be checked on pasted, pasted2 and pasted_long without a reader.

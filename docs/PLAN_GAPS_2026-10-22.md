# Closing the gaps before launch (plan, 2026-10-22)

JP: "We don't launch till we close the gaps else it'll die a slow
inconsequential death." Launch is held until every gate below passes.

## Why

Claude Code has its own memory. In the simulated comparison
(bench/claude_memory.py, generous to it) it answers more LoCoMo questions
than sourcedrecall: 77.7% against 66.9% on the first 354, 69.8% with our
standard notes model. Its context is about 11k tokens against our 0.7k, but
token savings are not a reason anyone installs a plugin. As a memory of
facts about the user, native memory is good enough and already there.

What native memory cannot do, and what a Claude Code user would pay
attention to:

1. It keeps only what the model chose to save at the time. Anything else
   is gone, and you find out when you ask.
2. It lives in one tool and one project folder.
3. It records conclusions, not what was tried, what failed and why.
4. Small local models have no memory of their own, and they take pasted
   text for the user's (our measured edge: 3 of 40 against 23 to 35).

The product to launch: the record of every session, in every project and
tool, dated and searchable with sources, that answers what native memory
dropped, including what was tried and failed. It sits beside native memory,
not in place of it.

## The gaps

### G1. Coding history (the main one)

Today the Claude Code hook keeps what the user typed and the assistant's
text; tool calls and their results are dropped, and the parser is built
for personal facts ("I moved to Brunswick").

Build: an episode record from each session, deterministic, no model call.
- From tool events (structured already): commands run with exit status,
  error lines, files edited, tests run and whether they passed. Keep the
  command and the first error line, not whole outputs (size, secrets: the
  existing secrets.py scrub runs on all of it).
- Episodes: an error or failing test, the attempts that followed, and what
  made it pass. "Tried X, failed with E; fixed by Y in file F" with date,
  project and session id.
- Decisions from the text: "let's use X instead of Y", "don't do Z, it
  breaks W", "we're going with". rgx already marks "decided with the
  assistant"; widen it to project decisions and their reasons, and record
  what each replaced (the same supersession as for personal facts).
- Conventions and commands that work ("the tests run with uv run pytest -x"),
  kept when repeated or stated.

Measure (pre-registered, JP reviews before it runs): a coding-recall set.
Questions a developer asks later: "what did we try first for the X bug
and why did it fail", "what command runs the integration tests", "why did
we drop library L", "which file had the fix for E". Sources, in order of
preference:
- public agent trajectories with real tool calls (SWE-agent / OpenHands
  trajectories on SWE-bench; licences to check), split dev / held out;
- JP's own Claude Code sessions in ~/.claude/projects, only if JP agrees,
  run on the Mac, never committed, results as counts only.
Systems: native memory (simulated, needs API credit, see Decisions), ours,
native plus ours, plain retrieval over the same sessions.

Gate: native plus ours answers clearly more than native alone (at least
10 points, paired p<0.05) on the held-out half, with the local reader; and
ours alone at least matches native alone on the "what was tried / what
failed" questions.

### G2. Search that is obviously useful

The pieces exist (profile_recall, rehydrate), but the tools are named and
described around a profile, so Claude does not reach for them when the
user asks "how did we fix this last time".

Build: one tool, search_history(query, project = this | all, since),
returning the passage, date, project and session, with the episode it
belongs to; tool descriptions written so Claude calls it for "last time",
"before", "we already", "what did we"; a /recall slash command and a
`sourcedrecall-run memory search` command for the user.

Measure: on the G1 set, how often Claude Code calls the tool unprompted
when the question needs history (a small run with Claude Code itself on
the Mac, once credit allows; else Qwen through an MCP client). Gate: it
is called for at least 8 of 10 such questions and rarely for others.

### G3. Beside native memory, not against it

Build:
- The session-start block leaves out what native memory already shows
  (read the project's memory folder; skip facts it states) and says what
  is new or changed since.
- For a native memory, the source: "where did this come from" returns the
  message it was written from, with its date.
- Import a native memory folder (and a ChatGPT / claude.ai export, which
  importers.py already reads) so nothing is lost if the user switches.

Measure: tonight's LoCoMo run gives the first number for free (Qwen
reading native's context and ours together, and how many of native's
misses ours answers). Gate: native plus ours clearly above native alone on
LoCoMo too, or the README says it is not.

### G4. Useful on day one, and visible

Today a new install starts empty and shows little until weeks of use.

Build:
- Backfill: on install, offer to store the user's past Claude Code
  sessions (~/.claude/projects transcripts; ingest_session already reads
  them) and Codex / Gemini sessions where present, in the background, with
  progress in `memory status`. The first session after install can then
  answer about last month.
- `memory show` as a local page: what it knows about you and each project,
  what changed and when, the episodes, and what it did not store and why
  (the "not stored" list from ontogr/agentic-graphrag), with forget and
  correct on each line.

Gate: on a fresh install on the Mac with a few months of sessions, the
backfill finishes in under 30 minutes on CPU and the first question about
an old session is answered with its source.

### G5. Cross-tool, tested

Hooks for Codex CLI, Gemini CLI and Cursor are written but untested in
those apps.

Build and test on the Mac: install Codex CLI and Gemini CLI, run real
sessions, check that they are stored and that a fact from one tool is
answered in another. Cursor needs its GUI (JP or computer use). One local
model setup end to end: an MCP-capable client with a local model
(llama.cpp or Ollama on JP's side, never Chris's Ollama), documented.

Gate: each tool listed in the README is tested in that tool, or removed
from the list.

### G6. The pitch

After G1 to G5: README opening, testers post and FAQ rewritten around
"the record native memory doesn't keep", with the native-memory comparison
stated plainly, including where native memory is better (personal facts,
LoCoMo). No token-savings claim. No "better memory than Claude Code's".

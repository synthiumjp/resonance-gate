# Adversarial review, 2026-10-21 (product-p2 at 3d1f88f)

Scope: public claims, measurement fairness, server code (capture, storage,
forget, privacy), fact extraction and the memory block, install and what
goes public. Read-only. Nothing was run on the Mac; on WSL only small
synthetic snippets (secrets regexes, prose.py rules with the classifier off)
and file counts. Held-out case text and JP's own memory were not opened.

Five Sonnet subagents, one per area. Their main findings were spot-checked
against the code before being listed here; corrections from that check are
noted. "Verified" means the code or file was read (or a number recomputed)
and the finding follows directly; "Suspected" means it follows from reading
but was not run.

## What matters most before launch, ranked

1. The README's opening makes the Mem0 comparison look better than the
   evidence. The lead comes from temporal questions, where Mem0 got dates
   only inside the message text (Mem0 2.2.1 takes no timestamp;
   bench/locomo/retrieve.py:243-245): temporal 57.0 vs 37.2 (local reader),
   74.8 vs 33.7 (Claude). Without temporal questions Mem0 is ahead: 67.5 vs
   71.3 local (708 vs 748 of 1,049), 77.6 vs 81.5 with Claude. The opening
   (README.md:35-44) says "level with Mem0" and "77.0% against 72.1%" with no
   caveat. The local table leaves out open-domain, where sourcedrecall is
   behind (36.1 vs 41.0; release_test_default/score.md:7). README.md:292-295
   gives the without-temporal figures as "without them (an earlier run)":
   they are the release answers without temporal questions, mislabelled (a
   reviewer took them for an uncommitted run). The LongMemEval "wins" in the
   opening are noise (knowledge-update 9 vs 6 discordant, p=0.61; temporal 21
   vs 12, p=0.16) and mix commits (72 from 53e0d9c, per-question files and
   plain retrieval from 75487ec, which has 73). Fix: opening says Mem0 leads
   without temporal questions and why; add the open-domain row; LongMemEval
   "no significant difference"; p-values beside every headline gap.

2. The first thing a new user is told to type does not exist. The plugin
   puts its commands in a private venv; `sourcedrecall-memory` and
   `sourcedrecall-import` are not on PATH (checked on JP's install), but the
   welcome message (claude_hooks.py:404, 413-414) and README.md:13, 392,
   449-450 tell the user to run them. The README install section never says
   a name must be set, and nothing says how to check it works. A failed
   install is sticky: install.failed is not tied to the version and is not
   cleared on update (sourcedrecall-run:168-183), so a user who fails once
   (no network, Debian without python3-venv) must find the plugin cache path
   to retry. Fix: `sourcedrecall-run memory|import ...` passthrough used in
   every message and the README; a three-line "after install" block; tie
   install.failed to REF.

3. Forget is not reliable while a session is open. The MCP server loads the
   memory once and never checks the files again (profile_memory.py:273-277;
   no mtime check anywhere). After `sourcedrecall-memory forget`, an open
   session keeps serving the erased fact, and its next write rewrites
   MEMORY.md from the stale copy, putting the forgotten text back on disk
   (_export_quietly). Also: sentences split at ". " so "Dr. Smith" breaks
   the match and _erase removes the hiding correction while the text stays
   in conversations.json (a rebuild brings it back); .before-rebuild-*
   caches and .corrupt-* copies keep the text; a forget during an ingest's
   parse can be undone by that ingest (keys read outside the lock,
   profile_memory.py:414). Fix: reload on mtime change before every read and
   before export; substring erase; erase backups; re-check keys inside the
   lock.

4. Wrong things are stored or shown as the user's (prose.py, rgx, memory_api;
   rules verified with synthetic text, the parser not run):
   - Rules in a pasted document become standing instructions shown at the top
     of every session: "look at what the docs say:\nAlways use the staging
     key. Never commit secrets." keeps both lines as the user's.
   - A first-name sign-off or "this is Amara from payroll" flips a paste to
     the user's own (prose.py:395-398; review 3.13 partly fixed).
   - A greeting to the assistant is taken for a letter and drops the user's
     own lines: "New session.\nHey Claude,\nI'm a nurse in Leeds..." keeps
     only "New session." (prose.py:573-579; lines[i:end+2] also takes one
     line too many).
   - _MOMENT drops lasting facts (rgx/__init__.py:176-181): "battery",
     "tired", "for now", "i'm back" anywhere in the sentence ("I work at a
     battery factory", "I'm back at Barclays as an analyst").
   - The session-start summary prefers the oldest facts: ties on mentions
     keep insertion order (memory_api.py:1996-1999), so past 15 facts the
     newest are cut. JP's store has 28.
   - A change within one session never supersedes ("I use Postgres" ... 40
     turns later "we switched to SQLite": both current; currency.py:581
     orders by date only).
   - The block is cut at 9,500 characters from the end, so [MEMORY RULES]
     goes first; standing instructions have no cap (claude_hooks.py:337).
   - A paste whose source is given in the next message is marked "[pasted
     in]" when shown, but its facts were stored as the user's (ingest calls
     _prose_only without `after`).
   - "About you" in MEMORY.md matches the owner by string prefix ("Anna" ->
     "Annabel's flat").

5. One bad turn loses a whole session, and tonight's fix keeps that. No
   per-turn try/except in ingest (profile_memory.py:521-552); a whitespace
   owner raises IndexError in prose.py:386/422 for any message with a source
   cue. The worker deletes its job on any exception (claude_hooks.py
   finally), so only kills are retried. _rerun_orphans: a job holding JSON
   that is not a dict raises AttributeError, and session_start catches only
   OSError, so the hook fails at every session start; two session starts can
   double-count tries; a week of orphans spawns that many 0.5 GB workers at
   once; .failed and .tmp files are never cleaned. Transcript reader:
   "[Request interrupted by user]" is stored as speech; turnOrigin is a
   whitelist (None, "human") for an undocumented field.

## Area 2. Measurement fairness

Same reader, judge, prompt and data for every system; the gold-answer audit
applies to all and is shown both ways.

- Context budgets differ: plain retrieval 10 turns / 356 tokens, Mem0 20
  memories / 722, sourcedrecall 12.65 lines / 682 (from the ctx files).
  REPRODUCE.md exports LOCOMO_TOP_K=5 for all three, which cannot reproduce
  the table. Mem0 and plain retrieval contexts and answers are copied from
  the 2026-10-03 run (release_measure.sh header), while the README says one
  run on 53e0d9c. Fix: state k and tokens per system, an equal-token plain
  retrieval, correct REPRODUCE. Verified.
- Pasted-text lead: the rules ablation (FM_OURS_RULES=0) exists for v11 with
  Qwen only; the plain-retrieval-plus-one-sentence control was never run.
  Refusal rates (v10: 35 of 40 "don't know" vs plain 15) are not in the
  opening sentence. The Claude column already shows the lead is a
  small-reader effect, and the README says so. Review 2.1 partly fixed.
- Audit asymmetry in the release rerun: copied competitor answers keep
  blind-audited verdicts, regenerated sourcedrecall answers keep raw judge
  verdicts (release_measure2.sh ~75); the packet still shows the judge's
  verdict (blind_audit.py:35). Review 2.3 open.
- LoCoMo test (conversations 2-9) was tuned on: at least 10 variants ran on
  it. The README admits it; the headline row should say so. The Qwen3-14B
  notes column (73.1%) is from 49561c4 and makes a model call per message:
  a different system. The multi-hop pre-registration ran cleanly (approved
  5d1bf56 before result 3986640).
- Pre-registration order checks out: every PREREG_HELDOUT_V5-V12 commit
  precedes its case file, and each case file its results.
- ai-memory adapter truncates to ~80 characters per message and 1,500 per
  page; AIM_FULL_OBS was never set. Plain retrieval in the false-memory sets
  is k=3, not stated in the README table.
- Claude column: one run, API default temperature, Claude as reader and
  judge with the lenient prompt; no failure counts committed (0 empty
  answers or verdicts found in the files).
- HaluMem: 2 of 20 users, per-item files not committed, plain retrieval on
  d6613e0.
- 10-12 status: 2.5 and 2.8 (retries) fixed; 2.1, 2.4, 2.6 partly; 2.2, 2.3,
  2.7 and the LoCoMo seed open.

## Area 3. Server code

- Items 3 and 5 above (forget, robustness).
- MCP profile_ingest still lets an agent speak as the user: role "user" is
  accepted, an existing conversation id appends to and renames a real
  session, nothing marks the turn as agent-written (mcp_server.py:118-126,
  profile_memory.py:459-485). Future dates and instructions are blocked.
- Secrets filter (synthetic run): whsec_ keys, bare user:pass@host, "the
  token <32 letters>", "mypassword is hunter2" pass; repeated "-----BEGIN
  PRIVATE KEY-----" takes 11.5 s at 336 KB, "1-" repeated 1.8 s at 240 KB.
  Fix: scrub in bounded windows; bound the BEGIN patterns.
- The lock fails open on any exception (profile_memory.py:117-122).
- Cursor stop still spawns a parser worker per agent turn (3.8 open);
  _erase_spools rewrites spool files without a lock.
- Import loads the whole file and rebuilds the memory per conversation
  (quadratic; 3.9 partly).
- browser.py is sound as read (loopback, Host allow-list, token with
  compare_digest, strict cookie, CSP, escaping).
- Windows (not run): os.replace over a file another process has open fails;
  unlink of a job the rerun has open fails.
- 10-12 status: 3.1, 3.3, 3.5, 3.6, 3.10 fixed; 3.2, 3.4, 3.7, 3.9, 3.16
  partly; 3.8 open.

## Area 4. Extraction and the block

- Item 4 above.
- Facts from assistant turns: only "report" clauses load, as hearsay, shown
  labelled in MEMORY.md, the browser and recall's "unconfirmed"; never in the
  session-start block (run_wire.py:222-247). JP's store has none, which is
  why none loaded; the 2026-10-20 handover note was too broad.
- Notes and the "quote" layout render `said` without _inert; ingest filters
  MARK on value and text, not source; so a missed paste with `"` or
  `[MEMORY` can forge a note (3.20 partly).

  flaky test" rewritten to "I fixed..."; "let's use X" in a coding chat
  taken as a decision.
- Claude Code's pasted_content tags are replaced with blank lines and the
  span then guessed; the tag is a definite paste signal.
- prose_only on 150 KB adversarial inputs: under 0.5 s each.
- 10-12 status: 3.12 mostly fixed ("add this to my notes:" still own), 3.13
  and 3.20 partly, 3.14 and 3.21 partly open, 3.18 fixed.

## Area 5. Install and what goes public

- The tag a fresh user's install clones (sourcedrecall-v0.5.2) does not exist
  on the public repo, which is still private. Known: this is the launch step
  (export, tag, push, PyPI together), then tools/clean_install_test.sh
  against the real URL.
- Item 2 above.
- Dependencies float (numpy, onnx, onnxruntime, tokenizers, huggingface_hub,
  nltk; `pip install --upgrade pip`): a release on launch day can break every
  fresh install. Fix: a constraints file from the tested set.
- Every upgrade re-downloads the 160 MB parser archive; the install lock
  expires after 60 minutes, shorter than a slow download.
- Windows: `py -3.12 -c` output may carry \r (Suspected); memory tools need a
  pasted `claude mcp add`; uninstall instructions are Unix only.
- Sizes disagree: hook says 0.9 GB of models, README 1.3 GB / 0.7 GB.
- Export: no host names, Tailscale addresses, keys or NAS paths found in
  the files it keeps; private paths are scrubbed. The final leak check
  matches only five patterns (misses a first name, .ts.net, 100.x
  addresses, C:\Users, other mail domains). bench/ ships ~193 MB in the
  clone the plugin makes. The wheel has no LICENSE or NOTICE. Confirm the
  product commit's author is the GitHub no-reply address.
- 10-12 status: 4.2, 4.3, 4.8, 4.9 fixed; 4.4, 4.5, 4.6 partly; 4.1, 4.11
  open.
